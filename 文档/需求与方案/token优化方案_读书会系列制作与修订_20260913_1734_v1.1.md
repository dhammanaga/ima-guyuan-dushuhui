## 一、06 线消耗结构诊断（制作场景）

| 消耗项 | 占比（估） | 问题 |
|---|---|---|
| 周子代理生成学员版（8×8万字节） | ~30% | **纯派生品却由 LLM 逐字重写**——05/07 线已验证可脚本生成，06 线未采用 |
| 每代理重复读样板/蓝图/规范（~175KB×8） | ~15% | 共享知识未外部化，8 代理重复载入相同大文件（Zylos 所指"协调税"） |
| 返工（W4 幽灵产出增补、W5 字数增补） | ~20% | 隐性大头：一次返工≈一个代理的量 |
| heavy 模型做机械任务（汇总/整理） | ~10% | 模型路由缺失：light 可胜任的任务用了 heavy |
| 主线程检索/验证/推送 | ~5% | 已基本脚本化，无明显浪费 |
| fetch 素材进入上下文 | ~20% | 必要成本（照录不虚构的前提），仅可微调 |

## 二、六项措施（制作场景，按收益排序，均不降质量）

### A. 双版本脚本化派生 ★最大杠杆（生成 token -30~35%）
- **做法**：子代理只写**主持人版**，埋两个 HTML 注释定界标记；学员版由 `_mk_student.py` 脚本零 LLM 生成：
  - `<!--W_LEAD-->…<!--/W_LEAD-->`：主持人导语（学员版转纯文本保留）
  - `<!--EXT_READ-->…<!--/EXT_READ-->`：延伸阅读（学员版挪到文末）
  - 脚本自动删：⭐速览块/⏱时间弹性指南/📌特别提醒/⚠️主持人操作行；替换标题与引导语标签
- **质量反升**：共读原文一致性从"约定+终检兜底"升级为"构造性保证"；`_qa_check` 继续双保险
- **依据**：05 线（13:20 完成）与 07 线（11:25 完成）均用此法通过终检，先例充分

### B. 交接最小化（每代理输入 -40~50%）
Glean 核心结论："**选择性上下文几乎总是胜过最大上下文**"。
1. **蓝图按周切片**：派发指令内嵌该周素材表（<1.5K tokens），不再让代理读全量蓝图（16.9KB）
2. **样板→体例契约**：提炼 3KB《体例契约》（章节骨架+信息行格式+1 个示例块），代理不读 150KB 样板全文；系列首个成品质检通过后，后续代理可改读同系列第 1 周成品（更直接）
3. **规范 checklist 化**：代理用 3KB 精简版（硬约束+自检清单），完整规范供主线程与人工查考
4. **指令模板化**：共性内容入文件（代理读文件），指令本体保持精简——每代理省的是"重复内嵌"

### C. 模型分级路由（汇总/杂务类 -60~80%）
Zylos：三层路由典型节省 50-83%。
- **heavy 只用于**：周文档创作（内容质量关键）、心理安全敏感周（W5/W6 型）
- **light 用于**：素材照录整理、README/CHANGELOG/00指南汇总、增补类机械修改、跨系列格式对齐
- **脚本（零 LLM）**：原文全集提取（06 线已做）、学员版派生（新增）、终检、查重、推送、zip

### D. 自检前置，减少返工（期望 -15~20%）
- 子代理指令固化：**产出后先程序化自检**（字符数硬线/禁用清单 grep/双版本锚点比对）全部通过才报完成
- 主线程只做抽验＋`_qa_check` 兜底（零 LLM）
- 06 线教训：W4 幽灵批次无自检→字符不达标→重做增补；W5 字数不足→二轮增补。预防一次返工≈省一个 heavy 代理

### E. 扇出控制（维持现状）
Zylos 建议 cap 3-5 agents/批——06 线 4/批符合，继续。大批量时宁可两批，不做 >5 大扇出。

### F. fetch 精准化（微调）
- fetch question 一律限定"完整照录与〈本周主题〉相关的原文段落"，避免整书无关内容涌入上下文
- 长文档 fetch 返回的 `[generated, not original text]` 标注照常保留（质量纪律不变）

## 四、执行清单（制作线开工时逐项落实）

1. ☐ 派发指令内嵌该周素材表＋体例契约（不再让代理读全量蓝图/样板）
2. ☐ 主持人版埋 W_LEAD/EXT_READ 标记 → `_mk_student.py` 生成学员版
3. ☐ 原文全集/终检/推送/zip 全脚本化（已有）
4. ☐ 汇总三件套（README/CHANGELOG/00指南）用 light 代理
5. ☐ 子代理指令末尾固化"自检通过才报完成"
6. ☐ 重做批次沿用"现状评估"指令（先评估再决定重写/增补，06 线已验证省算力）

## 五、★ 修订场景的省 Token 措施（v1.1 新增）

> 修订（把已完成的成品改为新口径）与制作的关键差别：**制作需要"创作"，修订只需要"定点改动"**。因此修订的最大浪费不是"写"，而是"读"。

### 5.1 诊断：修订的 token 浪费在哪

| 消耗点 | 是否必要 | 说明 |
|---|---|---|
| **把主持人版全文读进上下文** | ❌ 完全可避免 | 8 周 × ~35KB ≈ **10 万+ tokens 纯输入（纯浪费）** |
| 让 LLM 重写整篇 | ❌ 可避免 | 只需改局部字段 |
| 逐周分别对话 | ❌ 可避免 | 8 次来回＝8 倍交接开销 |
| 破冰/提问/去说教腔 的写作 | ✅ 必要 | 但只应产出几十字的"增量片段" |

### 5.2 三条铁律

1. **不把文档读进上下文**——主持人版 ≥30,000 字符、素材照录 ≥12,000 字符，一律用脚本在磁盘上处理；禁止用 read/fetch 把全文载入 LLM 上下文。
2. **不重写整篇**——只做定点替换 / 增量插入；LLM 输出"改动片段"，不是全文。
3. **不逐周对话**——8 周用一个脚本批量跑完，而不是 8 次来回对话。

### 5.3 分工表（谁做什么）

| 修订项 | 执行者 | 说明 |
|---|---|---|
| 六环节时长替换 | **脚本（零 LLM）** | 正则替换 6 处 ＋ 同步速览表/信息卡/弹性指南 |
| 派生学员版 | **脚本（`_mk_student.py`）** | 零 LLM |
| 终检 | **脚本（`_qa_check*.py`）** | 只输出"通过/失败＋计数"几行 |
| 朗读段标注 | **脚本（按字数切分）** | 机械取到 ~3,500–4,500 字并打标；必要时人工微调起止点 |
| 拉取/推送 | **脚本（Contents API）** | 落盘不进上下文 |
| 破冰/暖场 | **LLM（小片段）** | 仅产出 30–80 字增量，不重写整段 |
| 分层次提问 | **LLM（小片段）** | 仅产出 2–3 个问题 |
| 去说教腔 | **脚本初筛 ＋ LLM 收尾** | 正则先替换，剩余少数交 LLM |

### 5.4 量化对比

- 若把 8 周主持人版全文载入上下文：约 8 × 35KB ≈ 280KB ≈ **10 万+ tokens 纯输入（纯浪费）**。
- 脚本化后：LLM 输入仅"改动片段 ± 少量上下文"，输出仅每周约 200–300 字 → **总量可降约 90%+**。

### 5.5 提示词里怎么"写"才省 Token（关键）

派发/开工指令中**必须显式写入**如下约束，否则执行者会习惯性"读全文、重写全篇"：

```
【省 Token 约束（必须遵守）】
1. 不得用 read/fetch 载入主持人版或素材照录全文；这些文件一律用脚本在磁盘上处理。
2. 六环节时长替换、学员版派生、终检、朗读段标注：全部用脚本完成，不调用 LLM。
3. 仅"破冰/提问/去说教腔"三处可调用 LLM，且每次只提供"该环节现有 3–5 行 ＋ 要求"，
   让其输出增量片段（≤100 字），不得重写整段、更不得重写整篇。
4. 8 周用一个脚本批量处理；不要逐周分别对话。
5. 所有校验只输出"通过/失败 ＋ 计数"结论，不打印文档内容。
6. 报告 ≤300 字，不复述文件内容。
```

### 5.6 其他

- **复用模板库**：破冰、分层次提问做成"片段模板"，按主题取用，避免每周从零生成。
- **模型分层**：引导语写作＝heavy；机械整理＝light；批量改写＝脚本（零 LLM）。
- **单系列单会话**：系列间不续聊，防上下文膨胀；系列内少插话防 orphan。

> 本节与《读书会修订执行手册 v1.1》第五节一致——一句话触发修订时自动带上本约束。

## 六、预估节省（修订场景）

| 措施 | 依据 | 预估 |
|---|---|---|
| 文档不读入上下文（脚本处理） | 8 周全文 ≈10 万+ tokens 输入，全省 | -85~95% |
| 定点改写（不重写整篇） | 输出从"整篇"降到"片段" | 同上区间内 |
| 8 周批量脚本一次跑 | 免去 8 次交接 | -5~10% |
| 模板库复用 | 破冰/提问免从零生成 | -5~10% |
| **合计** | | **约 -90%**（相对"读全文＋重写"的天真做法） |
